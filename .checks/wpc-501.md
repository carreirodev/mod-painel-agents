# WPC-501 - Plans inside the agent frames, and a gap between the frames

Sources:

- https://linear.app/wpcsolutions/issue/WPC-501 - intent, criteria 1-22, Unresolved 1 (default: save and restore the Principal's plans per session), out of scope
- https://claude.ai/artifact/NqWHsk4iBUKjcDh4q9LQiF - **binding for the interface**: the plan block inside a card (dashed rule, `▤` title, state badge with time, bar, stages, steps, note, finished plans), the finished-subagent plan line, `trackHtml` for the bar and its pill text
- `mod-plan-pill-progress/plugins/plan-progress/hooks/register.tsx` (1.4.2) - the behaviour ported: `RULES`, `normalize`, `parsePlan`, the gate, the reminders, the Stop send-back, the tool's answer, `trackCells`, save and restore

Profile: light (no `AGENTS.md` in the repo declares one). Handoff: on, budget 150k.

## Out of scope

- The band above the prompt, sounds, settings window, update check, `hideAgentRows`, `subagentStatusLine`, the `⚡ tok/s` footer - the issue leaves them in plan-progress
- Bars on the desktop app and in VS Code - the pane is the terminal's; elsewhere the plan block draws its pill as text
- `/progress*` and `/plan-progress-*` commands; agent strips under the bars - the pane already shows agents
- Omarchy colours - the colours are the mockup's fixed ones (Omarchy only decides round ends, C21)
- Push or marketplace publish

## Landing

Touches `hooks/register.tsx` (the pane and every `on(...)`), adds `hooks/plan.ts` (pure plan logic ported from plan-progress), `hooks/track.ts` (the terminal bar's cells) and `hooks/plan-view.tsx` (the plan block a card draws), and `types/index.d.ts` (the `plans` state). Reuses the pane's `atom`/`update`, `stopwatch`, the 1 s tick and the `agents` rows (teammate flag) instead of plan-progress's `$.agent.list` lookups.

| One-way door | Literal shape | Alternative rejected |
| --- | --- | --- |
| A model-facing tool | `mcp__agents-panel__plan_progress`, input `{id, title, kind, stages, next, done, active, failed, state, note}` as plan-progress 1.4.2, answer `<id>: <pos>/<total>, <state>[, active "<step>"]` | a new name or input - breaks the rules and Claude's habit the issue keeps |
| The tool's schema is in the prompt from the start | `isDeferred: false` on `$.tool.register` | deferred behind ToolSearch (plan-progress's default) - the gate refuses the 4th edit until a plan exists, so the tool must be callable without a search first |
| Plans persisted in `$.state` and `$.store` | `$.state['agents-panel'].plans: Plan[]`, each with `madeBy?` (subagent that created it, absent = Principal) and `byAgent?` (subagent moving it now); `$.store` key `plans:<sessionId>` holding the Principal's plans, last 20 sessions | reading plan-progress's state - the issue forbids it; one `owner` field - cannot tell a handed-over plan's creator apart for the resume rule (C27) |
| Which Principal plan is "o plano atual" | every open Principal plan is drawn as a full block, in creation order; with none open the latest finished one is; every other finished Principal plan is one line under them | only the last plan drawn in full - an open plan created earlier would vanish from the frame while still asking for updates |
| Finished plans kept | at most 30 finished plans in `plans` (the oldest finished dropped first), the same bound as finished subagents | unbounded - the state grows for a whole session; plan-progress's 3 bars - too few for the CONCLUÍDOS lines |
| `plan_progress` calls count as a tool on the card | the card's activity row shows `▸ plan_progress` like any other tool | hiding the panel's own tool - the row would then lie about what the agent last called |
| "Claude trabalha" for the animation | the Principal's turn is live (`turn.start` until `turn.complete` without `agentId`) for any running plan, the subagent's row `running` for a plan it moves | animate every running plan always - criterion 12 says only while Claude works |

- Nothing else in this change is hard to reverse
